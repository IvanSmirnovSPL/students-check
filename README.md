# students-check

Проверка решений студентов: компилирует каждый `.cpp` из `students/problem_N/`,
прогоняет его на наборе тестов из `answers/N.txt` и пишет отчёт в CSV.
Дополнительно (независимо от прохождения тестов) для каждого студента
проверяется наличие `#include <vector>` и `#include <string>` во всех его
попытках по всем задачам.

Проверка идёт параллельно на нескольких ядрах: узкое место — компиляция
(`g++`) и запуск чужих бинарников, то есть отдельные процессы.

## Установка uv

Проект использует [uv](https://docs.astral.sh/uv/) для зависимостей
(официальная инструкция: <https://docs.astral.sh/uv/getting-started/installation/>).

Linux / macOS:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

Windows (PowerShell):

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

Через пакетный менеджер (если не хочется ставить установщиком):

```bash
pipx install uv        # или: pip install uv
```

Проверка, что всё встало:

```bash
uv --version
```

Если `uv` не найден после установки — откройте новый терминал (установщик
дописывает `~/.local/bin` в `PATH`) или добавьте его вручную:

```bash
export PATH="$HOME/.local/bin:$PATH"
```

## Быстрый старт

```bash
uv sync                            # поставить зависимости (pyaml, tqdm)
uv run python checker.py config.yml
```

Либо, если зависимости уже стоят в системе (и `uv` не нужен):

```bash
python3 checker.py config.yml
```

Путь к конфигу — единственный аргумент, по умолчанию `config.yml`.
Все пути внутри конфига (`answers_dir`, `students_dir`, `results_dir`)
относительны текущей директории, поэтому запускать чекер надо из корня проекта.

## Структура проекта

```
.
├── checker.py              # весь чекер: парсинг, компиляция, запуск, отчёт
├── config.yml              # настройки прогона (что и кого проверять)
├── answers/                # эталонные тесты: 1.txt, 2.txt, ...
│   ├── 1.txt
│   └── ...
├── students/               # решения студентов, разложенные по задачам
│   ├── problem_1/
│   │   └── Иванов_Иван_Иванович-contest_1_live_problem_1_attempt_1_time_12_30.cpp
│   ├── problem_2/
│   └── ...
├── results/                # сюда пишутся отчёты results_YYYYMMDD_HHMMSS.csv
├── pyproject.toml          # зависимости (uv)
└── uv.lock
```

Бинарники собираются во временной папке (`tempfile.TemporaryDirectory`) и
удаляются при выходе — на диске артефактов сборки не остаётся.

## Формат файла ответов `answers/N.txt`

Файл состоит из кейсов, каждый кейс — три служебные строки и два блока данных:

```
---CASE---
---IN---
<stdin, который подаётся на вход программе>
---OUT---
<ожидаемый stdout>
```

Правила:

* строки-маркеры распознаются по содержимому строки (`strip()`), поэтому
  отступы вокруг маркеров не важны;
* пустой вход и пустой ожидаемый вывод допустимы — важно только, чтобы строка
  `---OUT---` была на месте;
* если маркер `---OUT---` / `---CASE---` / `---IN---` пропущен, файл считается
  битым: чекер печатает ошибку с номером строки и **отменяет весь прогон**
  (код возврата 2). Это сделано намеренно: иначе вход следующего кейса
  приклеивался к предыдущему и верное решение получало FAIL;
* при сравнении отбрасываются незначащие хвостовые пробелы в строках и
  хвостовые пустые строки. Ведущие пробелы значимы (вывод бывает выровнен
  пробелами).

## Формат имён файлов решений

Имя файла должно содержать ФИО, вид работы, номер задачи и номер попытки:

```
<Фамилия_Имя_Отчество>-<что угодно>live|home_problem_<N>_attempt_<M>.cpp
```

Пример из реального набора:

```
students/problem_4/Аверин_Арсений_Алексеевич-contest_1_live_problem_4_attempt_2_time_18_29.cpp
```

Что извлекается из имени:

| Часть | Значение |
|---|---|
| `fio` | всё до первого `-` → `Аверин_Арсений_Алексеевич` |
| `surname` | первое слово ФИО → `Аверин` (используется фильтром `students`) |
| `kind` | `live` или `home` (ищется как подстрока в имени файла) |
| `problem` | число после `problem_` — должно совпасть с папкой `problem_N` |
| `attempt_no` | число после `attempt_` |

Файлы, имя которых не разобрать, пропускаются с предупреждением
`[warn] не распознано имя: ...` в stderr.

## Настройка `config.yml`

```yaml
# Кого проверять: all или список фамилий (можно "Фамилия" или "Фамилия_Имя")
students: all
# students:
#   - Аверин
#   - Иванов_Иван

# Какие задачи проверять (номера как в answers/ и students/problem_N)
problems: [4, 5]

# Сколько попыток проверять одновременно (параллельно по ядрам)
jobs: 5

# Параметры запуска
timeout_sec: 2
compile_timeout_sec: 20
compiler: g++
compile_flags: ["-O2", "-std=c++17", "-Wall"]
memory_limit_mb: 256

answers_dir: answers
students_dir: students
results_dir: results
```

| Ключ | Смысл |
|---|---|
| `students` | `all` — проверять всех; иначе список фамилий (`Аверин`) или полных ФИО (`Иванов_Иван`). Сравнение точное, по `surname` или `fio` из имени файла |
| `problems` | список номеров задач или `all` — тогда берутся все папки `students/problem_N`. Для каждого номера нужен `answers/N.txt`, иначе прогон отменяется |
| `jobs` | сколько попыток проверять одновременно. По умолчанию `5`; ставьте по числу свободных ядер. `1` — последовательный режим |
| `timeout_sec` | лимит на один тест (запуск бинарника) |
| `compile_timeout_sec` | лимит на компиляцию одного решения |
| `compiler` | компилятор C++ |
| `compile_flags` | флаги компиляции |
| `memory_limit_mb` | пока **не применяется** — зарезервировано на будущее |
| `answers_dir` / `students_dir` / `results_dir` | каталоги с тестами, решениями и отчётами |

Важно: `problems: all` берёт **все** папки `students/problem_N`, а файлы
ответов есть не для всех номеров (сейчас в `answers/` лежат 1–5, а папок —
1–7), поэтому `all` упадёт с ошибкой «файл ответов не найден». Перечисляйте
номера явно: `problems: [4, 5]`.

## Что происходит при запуске

1. Читаются и разбираются `answers/N.txt` по всем задачам. Ошибка формата хотя
   бы в одном файле — прогон отменяется (кода возврата `2`), потому что без
   валидных эталонов результаты бессмысленны.
2. Собираются попытки из `students/problem_N/*.cpp` с учётом фильтра
   `students`. Если ничего не нашлось — код возврата `1`.
3. Параллельно в пуле потоков (`jobs` штук): компиляция → прогон кейсов по
   порядку. Попытка останавливается на первом упавшем кейсе и фиксирует
   `тест i/N (answers/N.txt:строка): причина`.
4. Печатаются детали по каждой попытке и сводка по инклюдам `vector`/`string`.
5. Пишется CSV в `results/results_YYYYMMDD_HHMMSS.csv`.

Вид работы учитывается при подведении итога: зачёт по задаче ставится по
live-попытке, если она успешна, иначе по home (при наличии live-попытки,
пусть и неуспешной). Сначала рассматривается попытка с наименьшим номером.

## Отчёт в консоли

```
=== Детали проверок ===
[OK  ] Иванов_Иван | p4 | live attempt_2 (8/8) | vector=да string=нет
[FAIL] Петров_Пётр | p4 | live attempt_1 (3/8) — тест 4/8 (answers/4.txt:57): строка 2: ожидалось '5', получено '4' (строк: ожидалось 3, получено 3)
```

`(3/8)` — сколько тестов прошло до падения. Причина (`timeout`, `runtime
error`, `compile error`, diff) выводится через длинное тире.

## Колонки CSV

На каждого студента — одна строка. Для каждой проверяемой задачи `N`:

| Колонка | Значение |
|---|---|
| `pN_solved` | `yes` / `no` — решена ли задача |
| `pN_where` | `live` / `home` / пусто — по какой попытке зачтено |
| `pN_attempt` | `attempt_M` / пусто — номер зачтённой попытки |
| `pN_counted` | `yes` / `no` — идёт ли задача в зачёт (home без live-попытки не идёт) |
| `pN_tests` | `пройдено/всего` в лучшей попытке |
| `total_counted` | сумма зачтённых задач |
| `has_vector` / `has_string` | `да` / `нет` — встретился ли заголовок хотя бы в одной попытке студента |
| `vector_attempts` / `string_attempts` | `k/n` — в скольких попытках из скольких заголовок есть |

Файл пишется в `utf-8-sig`, чтобы Excel корректно открывал кириллицу.
